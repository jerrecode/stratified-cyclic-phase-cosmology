# Software and research architecture

SCPC uses a layered architecture in which scientific meaning flows in one direction:

```text
assumptions and action
        ↓
field equations and constraints
        ↓
validated numerical integrators
        ↓
derived observables
        ↓
likelihood adapters and inference
        ↓
figures, tables, and manuscript claims
```

A plotting routine must never become the source of a physical quantity. Paper figures consume serialized scientific outputs generated by the same tested functions used for analysis.

## Package boundaries

- `scpc.models.standard`: standard FLRW comparison models and background distances.
- `scpc.models.phase`: covariant canonical stratification-field baseline.
- `scpc.numerics`: integration, event classification, constraint monitoring, and provenance.
- `scpc.data`: release-manifest validation and controlled retrieval planning.
- `scpc.visualization`: deterministic plots from labeled arrays.

Future perturbation, Boltzmann, and inference adapters should be introduced as independent modules after the background model passes analytical and numerical validation.

## Model hierarchy

1. Standard FLRW models establish comparison and regression baselines.
2. The canonical SCPC phase field tests whether the simplest covariant interpretation is viable.
3. Only if required by explicit failures may scalar-tensor or effective corrections be introduced.
4. Perturbations and observables follow only after the background and Hamiltonian constraints are controlled.

## Data flow

Raw releases are external and immutable. The repository stores only manifests, schemas, selection recipes, checksums, and compact derived tables suitable for version control. Large raw files live under ignored `data/raw/`; transformed products live under `data/processed/`; numerical outputs live under `results/`; paper-local exports live under `paper/generated/`.
